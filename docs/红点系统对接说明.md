# 红点系统对接说明

本次按《红点系统设计规范》V1.0补充服务器红点。奖励发放、升级、消费、储钱罐购买/领取规则不变；新增红点统计、展示用未读状态与刷新逻辑。原有邮件、免费特邀刷新、特邀广告、联盟免费捐献、入盟申请红点保留。

## 消息

- 查询：`ReqRedDot`，消息号 `16400 / 0x4010`。指定模块且 `submodule=0` 查询该模块全部子模块；不指定模块查询全部。
- 推送：统一使用 `NotifyRedDot`，消息号 `16401 / 0x4011`。每条按 `(redDotModule, redDotSubmodule)` 覆盖旧值，不做增量加减。`count=0` 熄灭。
- 新增已查看：`ReqMarkRedDotRead`，消息号 `16420 / 0x4024`，无独立Res，接受后用 `NotifyRedDot` 返回该子模块最新状态。
- PB已同步至 `D:/java_projects/api/pb/core.proto`，含中文注释，旧字段及枚举序号不变。

`ReqMarkRedDotRead` 字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| module | RedDotModule | 必填，红点所属模块 |
| submodule | int32 | 必须为支持已读的具体子模块，不可传0清整个模块 |
| entityIds | repeated int32 | 本次实际查看的实体ID，最多200个；每日查看类不填 |

当前仅支持：`EMPLOYEE/4` 新雇员、`EMPLOYEE/5` 新羁绊、`ACTIVITY/14` 集合礼包。其他子模块不接受客户端清除；非法/不支持的请求忽略。客户端仍可使用 `ReqMarkRedDotRead` 精确确认已查看实体；此外，成功请求 `ReqGuestBonds` 并收到羁绊列表时，服务器会自动将本次返回的羁绊标记为已查看。

| 模块 | PB值 | 子模块 | 类型 | count含义 |
| --- | --- | --- | --- | --- |
| MAIL | 0 | 原有 | COUNT | 未读或附件未领邮件数，保持原逻辑 |
| PACK | 1 | 1 | COUNT | 可使用礼包格子数，堆叠100个仍计1格 |
| ACTIVITY | 2 | 4 | COUNT | 已满且可领取的储钱罐数，不改变中途领取规则 |
| ACTIVITY | 2 | 5 | COMMON | 拥有刮刮卡时1，否则0 |
| ACTIVITY | 2 | 10 | COUNT | 满足领取条件的签到奖励项数 |
| ACTIVITY | 2 | 14 | COMMON | 可参与集合礼包当日尚未查看时1；确认查看后当日0 |
| ACTIVITY | 2 | 25 | COUNT | 当天观看次数达标且尚未领取的视频福利档位数 |
| VISIT | 8 | 0 | COUNT | 留言未读条数，房主查看哪页只扣那页；访问别人留言不清对方红点 |
| SPECIAL_GUEST | 11 | 1/2 | COMMON | 原有免费刷新/广告可用提示，保留 |
| SPECIAL_GUEST | 11 | 3 | COUNT | 当前场景拥有的特邀游客邀请道具总数量 |
| EMPLOYEE | 12 | 1 | COUNT | 可招募卡池数，两个卡池使用相同消耗也分别计数 |
| EMPLOYEE | 12 | 2 | COUNT | 当前场景可升星的普通游客ID数 |
| EMPLOYEE | 12 | 3 | COUNT | 可升级或升星的雇员ID数，同一雇员最多计1 |
| EMPLOYEE | 12 | 4 | COMMON | 有新获得但未查看的雇员时1 |

| ALLIANCE | 13 | 1 | COMMON | 原有免费捐献提醒，保持原逻辑 |

| BUILDING | 14 | 1 | COUNT | 当前场景可投入升级进度/升级建筑或升级技能的建筑ID数，同一建筑最多计1 |

其他已有活动子模块保持普通红点语义。同类型多个活动先在服务器汇总，协议只发一条该类型红点，包含归零状态。

`RedDotType`：`COMMON=0`、`COUNT=1`、新增 `EXCLAMATION=2`。后者仅补协议能力，本次建筑按详细规范使用数字。前端显示优先级：正数数字 > 感叹号 > 普通红点。联盟总入口必须使用 `ALLIANCE/4`，不要只取数字类型的叶子，否则会漏掉免费捐献对总数的贡献；任务提醒不计入入口数字，联盟内部按钮仍分别使用子模块1、2、3。

## extra 明细

`extra`为JSON字符串；只在需要实体级显示的子模块中返回。空列表/空对象表示没有相应项，客户端应当覆盖旧缓存。未出现的可选动作列表按空处理。

| 子模块 | JSON示例 | 说明 |
| --- | --- | --- |
| PACK/1 | `{"gridIds":[1,3]}` | 可使用礼包格子ID |
| EMPLOYEE/1 | `{"ids":[11,12],"poolIds":[11,12],"guestPoolIds":[11],"guestPoolCount":1,"employeePoolIds":[12],"employeePoolCount":1}` | `poolIds/count`供招募总入口；游客、雇员卡池页签分别使用对应分组列表/数量，切换页签时不可只沿用当前页签状态 |
| EMPLOYEE/2 | `{"ids":[101],"starUpIds":[101]}` | 可升星游客ID |
| EMPLOYEE/3 | `{"ids":[11,12],"levelUpIds":[11],"starUpIds":[11,12]}` | 总计2，而不是两个动作列表相加为3 |
| EMPLOYEE/4 | `{"ids":[11]}` | 新雇员未读ID |
| EMPLOYEE/5 | `{"ids":[301]}` | 当前场景新羁绊未读ID；前端依配置映射到成员游客卡片 |
| EMPLOYEE/6 | `{"ids":[101,102],"starUpIds":[101],"bondGuestIds":[101,102],"newBondIds":[301]}` | 页签直接使用count；卡片按ids判断。starUpIds为可升星游客，bondGuestIds为未读羁绊的已拥有成员，ids为两者并集。示例count=2；查看羁绊仍发送EMPLOYEE/5及羁绊ID，服务器重算本项。外层招募入口汇总使用1、6、3、4，不能再叠加2、5造成重复计数 |
| BUILDING/1 | `{"casinoId":1,"ids":[101],"buildingIds":[101],"skillIds":{"101":[201]}}` | 101可升级且技能201可研究，总计仍为1；skillIds的key是建筑ID、value是Prop技能ID列表 |
| ALLIANCE/4 | `{"freeDonationCount":1,"applicationCount":2}` | 联盟总入口count为3；两个分量便于前端和测试核对，任务提醒单独读取ALLIANCE/3 |

示例：查看雇员11后发送 `module=EMPLOYEE, submodule=4, entityIds=[11]`。不会清除该雇员的可升级/升星数字。查看羁绊301传 `module=EMPLOYEE, submodule=5, entityIds=[301]`；按玩家当前场景处理。打开集合礼包并实际展示后传 `module=ACTIVITY, submodule=14`。

## 刷新与存储

- 登录/主动查询返回当前值；活动领取/加入后重算，3→2也推送；活动开关、在线跨天补刷新。
- 道具变更刷新礼包和刮刮卡。雇员与建筑由道具事件置脏，在同玩家下一次模拟经营tick合并刷新（当前调度间隔2秒），避免扣道具发生在升级状态写入前时发送旧结果。跨节点道具RPC也接入。
- 建筑等级、技能等级、CD等变化由tick检测。输入未变且未置脏不重复读背包，60秒兜底重算；仅展示内容变化才主动推送。
- 新雇员未读按玩家持久化；新羁绊按玩家+场景持久化；集合礼包记录查看自然日，重登不会重新亮当日已查看提示。旧账号不追溯把已有雇员/羁绊全部标新。
- 新增Redis键前缀 `red_dot_read:{playerId}:...`，已纳入PlayerKeyIndex。Mongo留言增加逐条 `unread` 与 `commentRevision`，旧记录按旧未读数兼容，分页/删除采用版本CAS，避免并发新留言被误清。
- 前端仍需接入新的PB、明细JSON和已查看上报。仅更新服务器，不会自动完成前端各按钮的红点表现。

## 等待确认的两处口径

1. 特邀游客规范同时要求“邀请道具数量”与“每天首次查看后消失”。本次先实现明确的道具数量，不因查看而清数量。是否另外增加每日首次查看子模块，需要确认。
2. 联盟任务正文要求每日首次查看提醒，表格又描述可领奖。当前联盟任务自动发奖，没有待领取状态，本次未改变奖励流程，也未擅自增加任务提示。建议确认后增加独立每日查看子模块。
