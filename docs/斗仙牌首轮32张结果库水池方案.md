# 斗仙牌首轮 32 张结果库水池方案

## 1. 目标

斗仙牌接入与南方前进相同的“离线模拟结果库 + 在线按水池选结果”机制，用机器人局回收或释放货币。调控对象只包含首轮四名玩家各 8 张、合计 32 张初始手牌；余下 20 张牌不记录顺序，在线开局时重新洗牌。

这样既能让初始牌面对整局结果产生可统计的倾向，又保留后续补牌、弃牌、特殊规则和真人操作带来的随机性。结果库表达的是期望收益，不是对单局结果的保证。

## 2. 结果库生成

每次生成先随机洗一副 52 张牌，截取四个模拟座位的 8 张首轮手牌。对同一组 32 张初始牌重复执行完整四回合模拟，每次把剩余 20 张重新洗牌，并按线上机器人当前策略完成摆牌和弃牌：

- 摆牌顺序为仙界、灵界、凡界，各区域使用现有 `DouXianHandEvaluator.findBestZone` 选牌。
- 弃牌概率与线上机器人一致：20% 不弃、20% 全弃、60% 随机弃 1～2 张。
- 飞升、牌池回收和“大胜/大败后下一回合收回三区牌”均按线上阶段顺序执行。
- 普通区域输赢和通杀加奖都按灵气差、底注和单笔封顶计算。

默认每组初始牌重复模拟 8 次。设指定真人座位集合在第 `r` 次模拟中的合计净收益为 `P_r`，房间底注为 `B`，结果库收益倍数为：

```text
multiplier = round(avg(P_r) / B)
```

同时记录收益标准差、正收益次数占比、四个模拟座位各自的期望收益和模拟器版本，便于后续分析稳定性、为连输或连赢玩家选择更合适的座位，并淘汰旧版本数据。

一组 32 张牌会分别产出 1 真人、2 真人和 3 真人三条记录。Redis 在收益区间外再增加 `real-1`、`real-2`、`real-3` 二级分区，防止不同真人人数的数据混用。0 真人和 4 真人的牌局不使用结果库，因为前者不影响货币池，后者的玩家净额合计恒为零。

## 3. 在线发牌

开局仍先生成完整随机牌堆。满足四人开局、真人数量为 1～3、水池配置存在且结果库已生成时，再执行以下步骤：

1. 根据当前房间水池相对初始值的偏差，选择 1～7 档水池模型。
2. 按模型 `typeProp` 权重随机选择收益区间；若真人达到连输阈值，则用 `addTypeProp` 对应档位的整套权重替换基础权重。
3. 从对应 `real-N` 分区随机抽取 3 条候选，使用后续模拟收益标准差最低的一条；目标桶为空时按收益边界距离使用最近的有数据桶。
4. 普通牌局随机打乱实际真人与模拟真人座位的映射；连输 5 局时把目标真人映射到期望收益最高的真人座位，连赢 5 局时映射到期望收益最低的真人座位，其余真人和机器人继续随机映射。
5. 按当前活跃玩家顺序把每人 8 张放到牌堆顶部，再把 32 张的补集 20 张现场洗牌并接到牌堆末尾。
6. 继续走原 `DouXianDealPhase`，因此客户端发牌流程和消息协议无需改变。

任何配置、Redis 数据或结果记录异常都会保留开局前已生成的随机牌堆，牌局不会因为调控系统不可用而中断。

## 4. 水池记账

每回合结算只使用已经成功转账的 `roundChanges`。设所有真人本回合实际净额之和为 `R`：

```text
poolChange = -R
```

- 真人合计净赢，`R > 0`，水池减少。
- 真人合计净输，`R < 0`，水池增加。
- 真人之间的转账会在合计中互相抵消；机器人之间的转账不进入水池。

水池按 `roomCfgId` 独立保存于 Redis `pool:300800` Hash，并在服务启动时按 `Room_Chess.xlsx` 的 `initBasePool` 执行 `putIfAbsent` 初始化，不覆盖线上已有余额。

## 5. 配置

`poker/resources/sample/poolResults.xlsx` 已在原 `poolResults` 页追加游戏类型 `300800` 的 7 个模型，没有新增或拆分 Sheet。

| 模型 | 水池偏差（万分比） | 作用 |
|---:|---:|---|
| 1 | `[2000, +∞)` | 强放水，明显提高真人正收益桶权重 |
| 2 | `[1000, 2000)` | 中放水 |
| 3 | `[300, 1000)` | 轻放水 |
| 4 | `[-300, 300)` | 标准池，收益权重对称 |
| 5 | `[-1000, -300)` | 轻吸水 |
| 6 | `[-2000, -1000)` | 中吸水 |
| 7 | `(-∞, -2000)` | 强吸水，明显提高真人负收益桶权重 |

收益桶边界为 `-1600、-800、-400、-200、-50、0、50、200、400、800、1600`，另保留正负哨兵边界。首版权重采用对称、渐进的保守曲线；上线前应使用足量结果库统计各桶容量，上线后再按实际 RTP 和水池恢复速度微调。

### 连续胜负权重

连续胜负按完整四回合牌局统计并保存在 Redis：整局净赢时正数连续加一，整局净输时负数连续减一，胜负方向改变后从 `+1` 或 `-1` 重新开始，整局净额为零则保持原值。

| 连续档位 | 权重效果 | 多真人处理 |
|---:|---|---|
| -5 | `≥50` 倍收益桶约 59.9%，负收益桶约 31.7% | 选择本桌连输最深的真人，并分配期望最高座位 |
| +5 | 负收益桶约 59.9%，`≥50` 倍收益桶约 31.7% | 优先选择本桌连赢最多的真人，并分配期望最低座位 |

两档都保留正负收益结果，没有设置成必输或必赢。一桌只触发一名真人和一个连续胜负档位；同桌同时出现连赢和连输玩家时，按南方前进现有逻辑优先处理连赢玩家。档位权重直接替换当前水池模型的基础权重。该机制仍只改变首轮 32 张的统计期望，不保证触发玩家当局输赢。

## 6. 生成与上线顺序

`poolResults.xlsx` 会在服务启动时加载。更新表后先重启对应 Poker 服务，再通过斗仙牌 GM 指令生成结果库。建议先生成小库验证：

### 后台 GM 页面

管理后台进入“游戏设置 → 结果库”，游戏选择“斗仙牌”。节点留空时由 GM 服务随机选择一个 Poker 节点；如果指定节点，必须选择实际承载斗仙牌的 Poker 节点。页面参数含义如下：

| 参数 | 预发布建议 | 正式库建议 | 说明 |
|---|---:|---:|---|
| 生成数量 | 1,000 | 100,000 | 随机首轮 32 张初始牌组数，每组会写入 `real-1`、`real-2`、`real-3` 三条记录 |
| 单组模拟次数 | 4 | 8 | 每组初始牌重新洗余下 20 张并跑完整牌局的次数，越大越稳定、耗时越长 |

斗仙牌不能与 Slots 游戏放在同一次提交中。点击“生成结果库”后任务异步执行，页面顶部每 5 秒刷新一次生成状态；“生成中”说明 Redis 分布式锁仍被占用，“空闲”表示任务已经退出。后台状态只表示任务是否运行，完整进度、分区记录数、空桶和最近切库时间仍通过玩家 GM 指令 `/douXianLibStatus` 查询。

若游戏字典还没有 `300800`，页面会显示内置的“斗仙牌”选项；后续仍建议在后台游戏字典补充 `300800`，保证其他使用通用游戏字典的页面也能识别该游戏。

### 玩家 GM 指令

```text
/generateDouXianLib 1000 4
```

生成任务在独立的单线程执行器中运行，不占用公共异步线程池。Redis 分布式锁使用 Redisson 看门狗自动续期，因此生成超过 30 分钟也不会因锁过期而启动第二个任务。生成期间继续使用当前旧库，全部记录写完后才切换双库指针；生成失败不会切换当前库。

随时查询状态：

```text
/douXianLibStatus
```

状态会返回配置校验结果、本节点生成进度、Redis 生成锁、当前库名、最近成功切库时间，以及 `real-1`、`real-2`、`real-3` 的记录总数和空桶。小库完成后，确认配置显示“有效”、最近成功切库时间已更新，并且三个真人人数分区都有记录。极端哨兵桶本身配置为 0 权重，数据为空不影响使用；所有实际带权重的收益桶应有数据，否则线上会向相邻非空桶降级。

验证无误后生成正式库：

```text
/generateDouXianLib 100000 8
```

第一个参数是随机初始牌组数量，范围 1～1,000,000；第二个参数是每组初始牌的后续随机模拟次数，范围 1～64。生成过程异步执行，并复用通用结果库的 Redis 生成锁、500 条批量写入和双库切换机制。100,000 组初始牌会产生约 300,000 条记录。

连输测试命令：

```text
/addDouXianStreak -5
```

该命令在玩家现有连续胜负值上累加指定整数。传入 `-5` 可验证连输档，传入 `5` 可验证连赢档。

建议按以下顺序投放：

1. 在预发布环境加载新的 `poolResults.xlsx`。
2. 执行 `/generateDouXianLib 1000 4`，用 `/douXianLibStatus` 确认配置和分区正常。
3. 执行 `/generateDouXianLib 100000 8`，期间重复查询状态，直到显示“生成完成”且最近成功切库时间更新。
4. 观察日志中的 `expectedMultiplier`、`stdDev`、`winRateBps`、目标桶降级次数和每回合 `poolChange`。
5. 小流量运行后，对比实际真人净收益与结果库期望收益；若偏差长期同向，再增加模拟次数或按真实操作数据修正模拟策略。

对应 Redis 数据如下，排障时可以直接核对：

```text
PokerResultLibCurrent:300800
PokerResultLib1:300800:{sectionKey}:real-{1|2|3}
PokerResultLib2:300800:{sectionKey}:real-{1|2|3}
PokerResultLibGenLock:300800
PokerResultLibLastGenTime:300800
pool:300800
```

## 7. 当前边界

离线模拟不知道真人下一步会如何摆牌或弃牌，因此统一使用当前机器人策略；它主要用于给首轮 32 张牌建立统计倾向。模拟结算包含单笔封顶，但没有虚构各玩家的开局余额，也不应用小额玩家保护和余额不足裁剪。线上水池始终按实际转账结果记账，所以这些差异不会造成水池账实不符，只会影响某条初始牌被归入哪个期望收益桶。
