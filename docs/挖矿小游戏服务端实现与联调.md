# 挖矿小游戏：功能分析、实现与联调

## 交付范围

依据《挖矿小游戏-系统策划文档v1.1》，在现有 Java 策略游戏服务中实现挖矿玩法。此仓库没有该玩法的客户端工程，因此不包含地图界面、美术、拖拽预览、音效、支付 SDK 或广告 SDK。

服务端入口已迁移到 `ploy/src/main/java/com/jjg/game/ploy/games/mining`，协议处理器为 `MiningMessageHandler`。六张 Mining 表位于 `ploy/resources/sample`，运行与赛季配置位于 `ploy/config/miningConfig.json`。玩法继续复用既有背包、充值订单、条件规则、特殊道具处理器及邮件。没有启动服务器、连接生产数据或部署。

| 范围 | 实现 |
| --- | --- |
| 挖掘 | 镐单格/连通校验，炸弹整行，挖机3×3；服务端扣道具、算耐久和奖励 |
| 地图 | 宽度由MiningMapGeneration.Width显式配置，可视高度取首阶段Height；绝对坐标；连通区域触底后滚动；仅下发可视格；旧行移除；响应单独返回滚动行数 |
| 生成规则 | 固定格、按深度过滤的随机权重、每段数量上限；表中固定格优先于随机深度限制 |
| 秘境/福利层 | 当前六张Mining表没有对应配置，不再运行代码内临时概率、奖励或福利层规则 |
| 背包 | 普通道具和存档一次提交；掉线重进继续；按 global 320 定时恢复镐；工具耗尽保留存档并返回结算提示 |
| 商店 | 多份购买、每日及永久限购、计数与矿石扣除；不支持的奖励在扣款前拦截 |
| 礼包 | 每日免费、前端看广告后直接领取、按配置扣钻石/道具购买 |
| 成就/每日任务 | 复用12701～12704数值条件；一次性成就、每日进度刷新、重复领奖保护 |
| 排行 | 当前赛季前300、自己的完整排名、深度相同按先到者/玩家ID排序；到期冻结奖励并通过邮件幂等结算 |

## 规则冲突与采用的口径

策划文档有若干示例与现行配置不一致，采用“现行配置优先，详细交互规则优先”的口径：

1. **炸弹**：文档总览写十字形，详细效果和 MiningTools 都写整行，因此实现整行，伤害取配置；不损伤花岗岩。
2. **花岗岩**：耐久9000；镐直接拒绝，炸弹跳过，挖机按配置伤害9999清除。
3. **矿石及工具产出**：奖励ID、数量、出现深度以 MiningCellType 为准。文档把“金矿获得银矿”等描述视为笔误，不据此发银矿。
4. **地图三元组**：MiningMapGeneration 原先把 FixedGrid/Randomizedgrid 声明成 map，会按格子ID去重且无法表达三元组。表头已改为 `list<list<int>{_}>{|}`，生成Bean对应 `List<List<Integer>>`，重复类型ID能够由通用配置加载器完整保留。
5. **三元组口径**：固定格解释为 `格子ID_段内行_列`，行列从1开始；同坐标后写覆盖。当前(3,2)同时配置花岗岩与炸弹，后者生效。固定格是明确布局，因此不受 MiningCellType.DropDepth 限制；随机项按 `格子ID_权重_每段数量上限` 解释，上限0为不限。
6. **超过现表192米**：继续复用最后一个阶段的高度、固定格和随机权重，不再使用代码内兜底ID或权重。正式难度曲线如需继续变化，应向 MiningMapGeneration 增加阶段。
7. **地图宽度**：MiningMapGeneration 增加 `Width` 整数字段，当前各阶段均配置为6。服务端不再通过 FixedGrid 中出现的最大列号猜宽度，并校验所有阶段的 Width 一致；加载到旧的2列存档时会按新宽度补齐地图，同时保留仍有效坐标的格子状态与玩法进度。
8. **工具与格子分类**：三种工具按 MiningTools.Damage 从小到大对应单格、整行、3×3；工具格通过其奖励是否指向工具表ItemID识别，资源格为其余有奖励格；墙体为耐久高于整行工具伤害的无奖励格。新增配置ID无需改代码。
9. **礼包模式**：直接读取 MiningBundleShop.BundleType：1免费、2广告、3消耗道具购买。免费/广告 `cost=0`；购买礼包的 `cost` 使用“道具ID_数量”，例如 `1980000_600` 表示600钻石，原数量不作金额换算。PB新增 `MiningBundleInfo.cost=12` 返回道具ID和数量，旧 `price=9` 保留为数量字符串，图标必须使用 `cost.itemId`。
10. **初始道具**：不额外虚构初始赠送。首次进入从现有背包读取，可领取表内免费礼包。
11. **永久/每日规则**：成就和永久购买数跨挖矿赛季保留；赛季只重置矿图和本赛季深度。每日按服务器时区午夜刷新。所有 Ploy 节点应使用同一时区。
12. **成就条件简写**：当前 MiningAchievement 使用 `12701_100`、`12703_1024035_50` 等省略通用主体参数的写法。服务端读取时补充“不限制主体”的 `0`，表内条件ID、道具ID和目标数值不需要改动；完整参数写法仍兼容。
13. **按时恢复镐**：读取 `global.xlsx` 的 ID 320，字符串格式为 `间隔分钟,恢复上限`，当前值 `10,400`。低于400时每10分钟恢复1个镐，离线期间按完整间隔累计，但只补到400；达到或超过400时停止计时。地图、礼包等其他途径仍可使库存超过400。

## 当前需要完成的运营/客户端接入

- **兑换表5007、5008暂不可买**：Goods为游客实体1025506、雇员实体1027401，其 Item 配置不进背包，也没有通用特殊资源发奖承载。返回 `available=false` 和 `UNSUPPORTED_NON_BAG_REWARD_*`，不扣费。应由策划改为已有可入背包的招募卡/碎片，或补充指定实体直发及重复拥有的处理规则后再做对应适配；不能简单发到普通背包。
- **赛季时间和排行奖励未提供**：`seasons=[]` 为常驻 `practice` 期，不做结算、不展示虚构倒计时。正式环境应先关闭入口，配置赛季时间、奖励并确认后再开启。保留过去的赛季条目，供重启补偿未完成的结算。
- **广告礼包**：前端完成广告后直接发送普通礼包领取请求，服务端不校验广告票据，只校验礼包类型和每日领取次数。
- **旧支付兼容**：`RechargeType.MINING_BUNDLE=14` 禁止创建新订单，仅保留历史报价订单的回调履约和失败订单释放能力；当前礼包走道具购买。
- **每日任务与赛季**：当前六张Mining表不包含每日任务、赛季时间或排行奖励，这些仍由 `miningConfig.json` 管理；地图、工具、格子、礼包、兑换和成就不再在JSON重复配置。该文件会作为默认配置打入ploy包，部署目录中的 `config/miningConfig.json` 仍可覆盖并热更新，避免漏传外部文件时接口静默返回空任务。
- **客户端**：需要实现玩法入口、网格、血条、操作动画、商店/成就/排行UI。主界面使用 `MiningInfo.tools` 更新镐、炸弹、挖机数量，使用 `MiningInfo.ores` 更新矿石数量；不要再读取已经移除的 `items`。`MiningInfo.nextPickRecoveryTime` 用于显示下一把镐的倒计时，到点后请求 `ReqMiningInfo` 取得服务器结算后的余额和新时间；值为0表示已达到恢复上限，不显示倒计时。兑换商店、礼包、成就、每日任务和排行均在打开对应界面时单独请求。
- **统计**：普通道具沿用既有库存日志，新增AddType 2201～2207及 `mining_action`、`mining_pick_recovery` 日志。广告曝光、前端局时长、插屏/Banner与UI转化漏斗仍需客户端埋点。

## 协议

消息类型沿用 `MINIGAME=0x28`，掩码 `0x28 << 12`，客户端协议号不变。挖矿命令由 Ploy 模块的 `MiningMessageHandler` 注册；Hall 模块的 `MinigameMessageHandler` 只保留大厅小游戏命令。

进入挖矿与 Hillo 等 Ploy 游戏一致：先从 Hall 发送公共 `ReqChooseWare`，参数使用 `gameType=400800`，`wareId` 必须传 `warehouse.xlsx` 中挖矿场次的真实ID（当前为 `4008004`）。Hall 完成游戏状态、场次及进入条件校验后，根据场次的 `gameID` 选择 Ploy 节点，保存 `gameType/roomCfgId` 并切换会话；所以首次进入时经过 `HallMessageHandler.onChooseWare` 是正常流程。节点切换完成后，挖矿请求由 Ploy 的 `MiningMessageHandler` 处理。退出使用公共 `ReqExitGame` 切回 Hall。

| 消息 | 完整cmd | 说明 |
| --- | --- | --- |
| ReqMiningInfo | 0x28100 | 进入、重连或刷新 |
| ReqMiningAction | 0x28101 | 操作 |
| ResMiningState | 0x28102 | 上述两个请求统一响应；action=0为刷新 |
| ReqMiningRank | 0x28103 | 当前赛季排行 |
| ResMiningRank | 0x28104 | 前300条和自己排名 |
| ReqMiningExchangeShop | 0x28105 | 打开兑换商店时请求 |
| ResMiningExchangeShop | 0x28106 | 兑换货币余额和兑换商品 |
| ReqMiningBundleShop | 0x28107 | 打开礼包界面时请求 |
| ResMiningBundleShop | 0x28108 | 免费、广告和付费礼包 |
| ReqMiningAchievements | 0x28109 | 打开成就界面时请求 |
| ResMiningAchievements | 0x2810A | 成就进度和领奖状态 |
| ReqMiningDailyTasks | 0x2810B | 打开每日任务界面时请求 |
| ResMiningDailyTasks | 0x2810C | 当日任务进度和领奖状态 |

`ReqMiningInfo`和每次`ReqMiningAction`返回的`MiningInfo`只包含矿图、工具、矿石和基础进度，不再携带兑换商品、礼包、成就或每日任务。排行榜原本就是独立查询，继续使用`ReqMiningRank`。客户端点击对应按钮时再请求面板数据，关闭和重新打开时可重新请求最新限购或任务状态。

各面板响应都返回当前`seasonId`和`version`。面板请求可能恰好触发跨日存档刷新，因此客户端收到面板响应后也要更新本地版本，后续`ReqMiningAction`使用最新值：

| 响应 | 主要字段 |
| --- | --- |
| ResMiningRank | `seasonId`、`version`、`ranks`、`self` |
| ResMiningExchangeShop | `seasonId`、`version`、`nextDailyReset`、`currencies`、`goods` |
| ResMiningBundleShop | `seasonId`、`version`、`nextDailyReset`、`bundles` |
| ResMiningAchievements | `seasonId`、`version`、`achievements` |
| ResMiningDailyTasks | `seasonId`、`version`、`nextDailyReset`、`dailyTasks` |

`MiningTaskInfo` 的 `nameLanguageId`、`descLanguageId` 分别提供名称和描述的多语言ID。成就取自 `MiningAchievement.xlsx` 的 `AchievementName`、`AchievementDescription`；每日任务取自 `miningConfig.json` 每项任务的同名字段，未配置时为0。

兑换商品和礼包使用不同结构。`MiningExchangeInfo`包含兑换商品、单份道具价格和限购信息；`MiningBundleInfo`包含礼包名称多语言ID、礼包内容、领取/购买模式、`cost`消耗道具列表、限购信息和广告冷却结束时间。`mode`直接取 `MiningBundleShop.BundleType`：1免费、2广告、3消耗道具购买，不再根据价格和展示顺序推断。`ResMiningExchangeShop.currencies`返回当前兑换表实际使用的货币余额。广告礼包尚有剩余次数时 `adCdEndTime=0`；次数用完后返回当天 `nextDailyReset`。当前配置没有单次广告间隔，不使用广告票据有效期充当冷却时间。

`MiningInfo`中的资源字段已经拆开：

| 字段 | 含义 |
| --- | --- |
| `tools` | MiningTools表识别出的镐、炸弹、挖机背包余额 |
| `ores` | MiningCellType奖励识别出的非工具矿石余额 |
| `nextPickRecoveryTime` | 下一次按时恢复1个镐的毫秒时间戳；达到 global 320 配置的恢复上限时为0 |

两个字段虽然都使用`ItemInfo`元素，但分类由服务端根据表结构完成，客户端不需要从一个混合列表中再判断道具类型。

`ReqMiningAction` 必填当前 `seasonId`、`version`；`count` 必须显式传1，兑换允许1～10000且不得超限。客户端应串行提交操作，收到结果后更新版本。

| action | id含义 | 其他字段 |
| --- | --- | --- |
| 1 挖掘 | 工具配置101镐、102炸弹、103挖机 | row绝对行、column列，均从1开始 |
| 2 兑换 | MiningExchangeShop ID | count份数 |
| 3 礼包领取/购买 | MiningBundleShop 商品ID，支持全部BundleType | count=1；1免费、2广告直接领取，3按cost扣道具；广告播放由前端控制 |
| 4 成就领奖 | MiningAchievement ID | count=1 |
| 5 每日任务领奖 | miningConfig.dailyTasks ID | count=1 |

购买礼包统一发送 `ReqMiningAction(action=3,id=礼包ID,count=1,seasonId,version)`，例如6003消耗600钻石获得10镐。不要调用 `ReqGenerateOrder`；服务器拒绝新的挖矿现金订单。前端从 `MiningBundleInfo.cost` 读取图标和完整消耗数量（免费/广告为空列表），以 `ResMiningState` 更新奖励、存档版本和剩余工具，以通用货币变化通知更新钻石余额；余额不足等失败后刷新挖矿状态再提交新请求。

`ResMiningState.info.cells`只有操作完成后的可视窗口。`changed`只记录本次受击且在滚动后仍处于可视窗口内的格子，不包含已经滚动移除的旧格子。`rewards`是本次全部奖励的合计；`rewardCells`逐格返回本次被挖开且实际产出奖励的来源格子，每项包含操作前绝对行列、MiningCellType ID和该格子的实际奖励，前端可据此在对应格子播放掉落表现。无掉落格不进入`rewardCells`，兑换、礼包和领奖等非挖掘操作也不返回该字段。`scrollRows`表示本次地图向上滚动的行数，`0`表示未滚动；其值等于本次操作使地表可达的最深前沿推进的行数，范围工具一次打通多行时可能大于1，客户端必须按字段值处理。非挖掘操作和普通未触底挖掘返回0。

发生滚动时，`info.topRow`已经是滚动后的最终绝对行。客户端按`scrollRows`向上移动地图、移除顶部对应行，再以`info.cells`补齐最终窗口；`changed`只用于仍可见受击格的耐久和动画更新。新生成行不会被同一次炸弹/挖机继续击中。`hp=0`为已挖开，类型保留用于表现。

连通只认上下左右四方向：开放区域必须通过共享边的空格连到地表，斜角接触不连通。未打开格仅在正交邻接可达开放格时返回 `connected=true`（真实地表第一行直接可达）。空格传播、镐的目标校验和滚动来源均遵循此规则。

`info.depth`为最深**挖开**行；窗口底部标尺可由 `topRow+visibleRows-1` 计算，二者不要混用。`secretId`仅为旧存档兼容字段，当前表驱动生成不会创建秘境。

`toolsExhausted=true`只提示工具表内所有Item均耗尽，不删除地图或资源；玩家补充道具后继续。`resourceValue`为格子表识别出的资源累计数量总和；当前表没有资源估值字段，因此不再使用代码内铜30、银100、金500的临时系数。

按时恢复的时间游标保存在挖矿存档中，并与镐奖励在同一个背包CAS事务中提交，重启、重连和并发请求不会重复发放。客户端倒计时仅用于展示，实际数量以服务器请求时结算为准。若一次离线跨过多个完整间隔，`ResMiningState.rewards`合并返回本次补发数量，`MiningInfo.tools`返回结算后的最终余额，但补发后不会超过恢复上限。达到上限时游标清零；使用镐后低于上限，则从该次操作时间重新开始一个完整恢复周期。旧存档没有恢复游标时，以账号最近离线时间作为一次性迁移起点并立即补算；没有有效离线记录的新玩家从首次进入时间开始计时。

`code=200`为成功，其余沿用项目Code。`reason`补充机器可读原因：

| reason | 客户端处理 |
| --- | --- |
| STALE_VERSION | 丢弃旧操作，重新ReqMiningInfo；不自动重放付费/领奖操作 |
| CELL_NOT_CONNECTED | 提示格子未连通 |
| WALL_REQUIRES_EXCAVATOR | 提示该格需挖机 |
| CELL_ALREADY_OPEN / NO_DIGGABLE_CELL | 不播放成功扣除动画 |
| OUTSIDE_VISIBLE_MAP | 刷新地图；不允许回挖旧区域 |
| ITEM_TRANSACTION_FAILED（code=420） | 道具不足，显示获取入口 |
| PURCHASE_LIMIT | 商品售罄/数量超限 |
| NOT_ENOUGH_BUNDLE_CURRENCY | 钻石/货币不足，刷新余额及挖矿版本 |
| DELIVERY_REQUIRES_RECONCILIATION | 特殊发奖结果未知，联系客服/后台核账；不要重放 |
| SPECIAL_REWARD_FAILED_REFUNDED | 明确发奖失败，矿石和限额已返还 |
| SERVER_ERROR_REFRESH_STATE | 结果可能已提交，先刷新再决定下一步 |

## 持久化与并发

- `PlayerPack.miningState`存JSON，随背包原有Redis→Mongo迁移保存；旧玩家字段为空时懒初始化。
- 普通挖掘、普通商品兑换、普通奖励领取、支付发货都调用 `PlayerPackService.exchangeMiningItems`：背包锁内校验旧存档字符串，在**一次背包写入**里保存新状态、扣除和奖励。因此同一版本并发请求只会成功一次。
- 玩法另有玩家分布式锁，串行化限额、报价、外部奖励处理。赛季读写锁阻止结算过程中写入本赛季深度。
- 不对玩法存档做单独的“先发奖后保存”，也不在背包锁内调用特殊道具处理器，避免后者重入背包覆盖未提交数据。
- **跨系统特殊资源不是分布式事务**：先原子扣矿石并保存delivery日志，再调用已有特殊资源入口。明确失败则退款恢复旧存档；调用异常/结果未知则保留delivery并禁止重试。核账后仅由服务端调用 `reconcileDelivery(player, deliveryId, granted)`：true确认已发，false确认未发并退款。不得在未核账时盲目调用。已有特殊资源入口返回false的语义仍是“失败且无净入账”，跨节点/宕机需要部署环境验证。
- **货币购买**：钻石等货币通过 `PlayerPackService.removeItems` 扣玩家货币余额，不查普通背包。先CAS保存购买预占和delivery，再扣货币，最后CAS提交普通背包奖励并清除delivery。明确余额不足撤销预占，异常/未知结果保留记录禁止重扣；并非跨存储原子事务。核账后由服务端调用 `reconcileCurrencyPurchase(player, deliveryId, deducted)`，true确认已扣并补发，false确认未扣并撤销预占；两者都不再次扣款。货币礼包当前只支持普通背包奖励。
- 历史现金订单的报价预占仍可通过 `onOrderCreationFailed` 或 `releaseClosedOrder` 释放；不新增报价。
- 支付订单ID与发货一起记录在存档中，重复回调返回成功但不重复发货；即使玩法关闭或赛季已结束，已支付的有效报价仍履约。

## 排行与赛季结算

`miningRank` 保存参赛登记和排行投影。所有玩家先登记再创建存档。写入背包后若排行同步失败，下次请求或赛季结算会从登记参赛者的存档恢复；因此网络异常可能造成短暂显示延迟，不影响最终补偿。

排序规则：depth降序，reachedAt升序，playerId升序。depth=0不入榜。列表最多300，自己排名可超过300；奖励仅按配置名次范围。

定时任务每分钟检查结束赛季。第一步持久化结算快照到 `miningSettlement`，冻结前300的名次和奖励；第二步逐人按业务键 `mining:rank:<seasonId>:<playerId>`发邮件并保存进度；最后记录completedAt。失败重试不重新采用热改后的奖励，已经完成的赛季不再发奖。使用既有 MailService 的幂等邮件机制。

正式启用前确认Mongo存在以下索引（此任务没有对任何数据库执行）：

```javascript
db.miningRank.createIndex({seasonId: 1, depth: -1, reachedAt: 1, playerId: 1}, {name: "season_depth_time_player"})
```

`miningRank._id=seasonId:playerId`，`miningSettlement._id=seasonId`，依赖Mongo默认_id唯一索引。还需保留既有邮件业务键唯一索引。

赛季配置结构（以下是结构示例，时间与奖励必须使用运营确认的实际值；不要直接复制0时间）：

```json
{
  "id": "mining_s1",
  "startTime": 0,
  "endTime": 0,
  "rewards": [
    {"from": 1, "to": 300, "items": {"1024034": 5}}
  ]
}
```

禁止重叠时间、重复赛季ID、重叠奖励名次范围。不要复用已结算的seasonId。改变赛季配置前应完成过渡方案；不要在玩家仍需结算时删除旧赛季。正式运营不应从已有赛季回退到practice。
